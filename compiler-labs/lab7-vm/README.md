## 这个 lab 解决什么问题

lab6 结束时编译器有了清晰的"腰"，但执行引擎在**作弊**：`irvm.c` 让 C 递归
兼任 MiniC 的调用栈——param 压进一个辅助数组，call 直接调 C 函数，返回靠
C 的 `return`。递归能跑，但那层栈属于 C 运行时，看不见也讲不清。
lab7 把它摊开成第 7 章说的样子：

```
前端(lab1~5)                    后端(lab7~)
源码 → token → AST+类型检查  →  四元式 IR  →  栈式VM(本lab) → x86-64(lab8)
                                              ↑ 程序第一次真正"自己跑"
```

MiniC 语言随 lab6 的数组升级**同步演进**（前端文件与 lab6 逐字一致；
旧测试集原样沿用，输出必须逐字节一致）。执行侧的变化全部发生在
"怎么执行 IR"：

- 显式运行时栈 `stack[]` 与帧指针 **fp/sp**——每层调用一块活动记录；
- call/return 成为真实的控制流转移：压返回地址、跳转、按 fp 收帧弹回，
  不再借道 C 递归；
- 参数住进帧内固定槽位（`fp+offset` 寻址），不再按名字挂链表；
- 无穷递归从"段错误"变成一句中文报错：`栈溢出（递归太深？）`。

执行引擎从此三台并存，互为对拍：默认 **vm**（本 lab）、`-irvm`（C 递归
解释器）、`-eval`（树遍解释器）。


`-trace` 输出节选（`print fact(3);`，stderr；stdout 照常可对拍）：

```
[vm] call fact      深1   fp=4     sp=11    实参(n=3) 局部3格
[vm] call fact      深2   fp=12    sp=19    实参(n=2) 局部3格
[vm] call fact      深3   fp=20    sp=27    实参(n=1) 局部3格
[vm] ret  fact      深2   -> 1  回到 fact:8  sp=19
[vm] ret  fact      深1   -> 2  回到 fact:8  sp=11
[vm] ret  fact      深0   -> 6  回到 main:2  sp=3
```

fp 每次 +8：一层帧 = 3 格帧头（旧 fp / 返回段号 / 返回 pc）+ 4 格局部。
三条 call 时三个帧**同时**在栈上——递归的正确性第一次看得见。

## 理论精要

### 1. 存储组织与活动记录（7.1/7.2 节）

一台只有五样东西的机器：全局数据区、运行时栈、sp、fp、累加器 acc
（返回值的唯一通道，相当于真实 CPU 的 rax）。指令集就是 lab6 的四元式，
一条不改——变的只是执行 call/return 的方式。每次调用压入一个**活动记录**
（activation record，即帧 frame）：

```
   低地址
 ┌──────────────┐
 │ 实参 n-1..0  │ caller 的 param 压好，call 后原样留给被调方
 ├──────────────┤
 │ 返回 pc      │ ← fp+2   回到 caller 的下一条指令
 │ 返回段号     │ ← fp+1   跨段跳转得连"回到哪一段"一起记
 │ 旧 fp        │ ← fp+0   fp 链：顺它能一路摸回所有祖先帧
 ├──────────────┤ ← fp
 │ 局部槽 ...   │ ← fp+3 起：形参占 0..nparams-1，其后是其他局部
 └──────────────┘ ← sp
   高地址
```

帧头三格里最经典的是**返回地址**：call 把"回去的位置"压进被调方的帧，
return 再弹出来跳回。递归由此不再需要任何外部帮助——每层只是多压一个帧，
各层的返回地址天然不同。

### 2. 调用序列：caller 与 callee 的分工（7.2 节）

龙书把一次调用拆成两半，本 VM 逐条对应：

```
caller: param ×n        实参依次压栈（求值早已完成——gen 保证 param 前
                        实参代码已全部生成）
        call f,n        压(旧fp, 自身段号, pc+1)；fp = sp−3；序言把实参从
                        实参区拷进形参槽、其余局部清零；sp 越过整个局部区；
                        跳到 f 开头
callee: ……执行……
        return y        acc = y（无 y 取返回类型零值）；sp = fp 收掉整个
                        帧；fp = 旧fp；弹返回地址跳回
caller: 自己清掉那 n 个实参槽（cdecl 风格"调用者清栈"）——回去落点的
        前一条恰是发起调用的那条 call（不变式：return 只落在 call+1），
        argc 就在那条指令里；再把 acc 存进结果临时
```

"谁清实参"是个真正的约定分歧点：cdecl 让 caller 清（支持可变参数，
printf 因此可能）；Pascal/stdcall 让 callee 清（N 个调用点只清一次，
省代码）。本 VM 取 cdecl，练习 1 让你改成另一派并对拍。

### 3. 名字 → 槽位：装载期的一次性绑定

gen 已保证 IR 名全局唯一（同名加 `@N` 后缀）、临时编号全程序不复位，
于是两级寻址可以**纯静态推导**：

- funcs[0]（主段）里被赋值过的名字 → 全局区各占一格——顶层声明的变量
  就是全局变量，主段的临时也落这里；
- 函数段里其余名字 → 本函数帧内的偏移（形参先占 0..n-1，恰与实参区
  对齐）。**帧大小编译期即知**。

这正是第 7 章的核心思想："相对 fp 的偏移编译期确定，运行期只做
`stack[fp+off]`"。对比 lab6：每读一个变量都要沿帧链 strcmp 一圈；
这里装载期绑定一次，执行期零查找。真实编译器里"符号 → 帧偏移"的
绑定就发生在这一步，寄存器分配只是给部分槽位再升一级。

### 4. 非本地数据与参数传递（7.3/7.4 节)

MiniC 无嵌套函数，所以**不需要 static link/display**：函数只看得到全局区和
自己这一帧。寻址规则因此简单到一句话：本帧表里没有的名字回退全局区——
这条规则就是作用域语义在运行时的投影（函数看不见别的函数的局部）。
参数传递只有值传递一种：`try_set(v)` 改的是被调方帧里的形参槽，实参
毫发无损——`tests/cases/vm.mc` 第 3 组专测这一点。递归中的同名局部
（每层 `down` 都有一个 `pre`）落在各自的帧里，扁平名字环境必错的程序
在这里自然正确。

## 练习

1. **换成 callee 清栈**：把实参清理从 Q_RETURN 的 caller 侧挪进 callee
   （用自身 nparams），观察哪些代码变短了、可变参数为什么从此不可能——
   三引擎对拍保证你改对了。
2. **完整帧打印**：增强 `-trace`，按槽列出整帧内容（旧 fp / 返回地址 /
   实参 / 各局部），在递归最深处打一张全栈快照——你会得到一张教科书
   7.2 的图。
3. **static link**：让 parser 接受嵌套函数，帧头再加一格 access link，
   内层函数经它读写外层局部——亲手体会 7.3 为什么需要 display 或
   静态链。
4. **按引用传参**：加 `int &x` 形参，VM 里存"(帧, 槽)"地址而非值，
   `swap(a, b)` 就能真换了——7.4 节按引用传递的最小实现。
5. **尾调用优化**：`return f(...)` 且类型匹配时不压新帧、直接复用当前帧。
   动手前先用 `int loop(int n){ return loop(n+1); }` 观察 STACK_MAX 行为，
   改完后同一个程序永不溢出——这就是 Scheme 实现的立身之本。
6. **数组寻址**：数组已经随 lab6 同步进来——装载期给每个数组在帧里
   预留连续 len 格，Q_LDX/Q_STX 按"基址槽 + 下标"取元素。试着把
   `-trace` 增强到能打印整个数组块；再想想为什么全局数组和局部数组
   的基址一个在 globals[]、一个跟着 fp 走——这正是静态分配与栈分配
   的分野（7.1/7.2 节），lab8 的 x86-64 会把同一个计算变成一条变址
   寻址 `[rbp+off+i*8]`。

## 龙书 vs 现代

- **参数早就不走栈了**：x86-64 System V 前 6 个整型参数放寄存器，
  Windows 是另外一套；本 VM"实参一律压栈"是 32 位时代的画像。
  但一旦参数多于寄存器数，剩下的照样进栈——帧布局的知识没过期。
- **fp 可以不要**：`-fomit-frame-pointer` 把 rbp 挪作通用寄存器后，
  栈回溯改靠 DWARF CFI/eh_frame 元数据描述。本 VM 的 fp 链正是这套
  元数据的手工前身；调试器"看调用栈"用的还是同构的信息。
- **字节码 VM 谱系**：JVM 的"局部变量表 + 操作数栈"、CPython 的
  frame object、wasm 的栈机——都是本 lab 五样东西的不同放大。真实
  解释器用 threaded code/间接跳转取代大 switch，分派开销差数倍。
- **栈的方向与安全**：真实栈向低地址生长（本 VM 向高），配合历史
  上"缓冲区向高写"造就了栈溢出攻击一整门攻防——canary、ASLR、NX
  都是为它而生。教学 VM 单向生长 + 定界检查，把这整套问题关在门外。
